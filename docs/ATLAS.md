# Atlas report bot

Natural-language reporting over the Atlas ERP PostgreSQL database, with multi-turn conversations
(up to 6 questions per session) and layered safeguards. Built on PromptQuery's introspection,
validation and CLI foundations.

## How a question is answered

```
question ─▶ follow-up rewrite ─▶ generate (plan + SQL) ─▶ as-of date rewrite
         ─▶ strict validation (allowlists, tenant scoping, row cap)
         ─▶ read-only, tenant-scoped execution ─▶ repair loop ─▶ summary + audit log
```

`Engine.ask(session_id, text)` in `src/promptquery/engine.py` is the single entry point; the CLI
(`prq-atlas`), the HTTP API and the evaluation harness all call it, so what is measured is what ships.

| Concern | Where | Why it exists |
|---|---|---|
| Curated schema pack | `src/promptquery/atlas/pack/*.yaml`, `pack_loader.py` | Atlas enums are plain VARCHAR, 97 cross-module `*_id` columns have no FK, and "posted/open/revenue" are business rules. Introspection alone cannot tell the model any of this. The pack is merged with the live schema, so a column that does not exist can never reach the prompt. |
| Metric definitions | `pack/metrics.yaml` | Mirror Atlas's own KPIs (open orders = CONFIRMED/PARTIALLY_DELIVERED, aging buckets, cash position, OTD...). |
| Deterministic "today" | `atlas/asof.py`, `PQ_AS_OF` | Demo data ends 2026-07-06; "last month" must not depend on the wall clock. Stray `CURRENT_DATE`/`now()` are rewritten. |
| Few-shot examples | `atlas/examples.py`, `pack/examples.yaml` | 46 verified question-to-SQL pairs plus 4 refusal examples; the closest few (TF-IDF over the question) are shown as patterns. A test requires each to run on real data and to differ from every eval scenario, so the eval stays honest. |
| Follow-ups | `conversation/` | Intent classification (NEW/REFINE/DRILL/REFERENCE/RESET/CLARIFY), ordinal resolution ("the first one") from real result rows, REFINE edits the previous SQL. |
| Turn cap | `conversation/state.py` | 6 questions per session; the 7th returns `status: "turn_limit"` without calling the model or database. |
| Repair loop | `engine.py` | Validator rejection, database error, or a suspicious empty result each trigger a bounded re-prompt (default 2). |

## Safety model (defence in depth)

1. **Database role** (`sql/atlas_bot_role.sql`, generated by `python -m promptquery.atlas.security`):
   non-superuser, read-only default, 15 s statement timeout, `SELECT` on an allowlist only,
   column-level grants on `hr_employees` (no salary / national id / tax id / birth date / bank
   account), no access to users, sessions, API keys, audit log, payroll, RBAC tables.
2. **Row-Level Security** on every tenant table keyed on a transaction-local `app.tenant_id`
   (an unset value raises: fail closed). `ENABLE`, never `FORCE`, so Atlas's own connection is unaffected.
3. **SQL-level tenant scoping**: every base-table reference is rewritten into a tenant-filtered
   subquery (`safety.scope_to_tenant`), so isolation holds even when connected as a role RLS does
   not apply to.
4. **Strict validator** (`safety.validate_report_query`): one statement; no DML/DDL/`INTO`/`FOR
   UPDATE`/`SET`/`COPY`/transactions; table, schema, column and function allowlists; `SELECT *`
   expanded to readable columns only; `LIMIT` injected or clamped; SQL regenerated from the AST
   (comments dropped); length cap.
5. **Execution** (`Database.run_scoped`): `BEGIN READ ONLY` per call, tenant set per call, per-call
   timeout, `fetchmany(cap+1)` (default cap 1000, `truncated` flag), always rolled back.
6. **Untrusted data**: previous result rows are fenced in `<prior_result untrusted="true">`,
   sanitised and length-capped; the system prompt says they are data, never instructions.
7. **Audit**: every attempt is appended to a JSONL log (`PQ_AUDIT_LOG`).
8. **API**: set `PQ_API_KEY` to require an `X-API-Key` header on every route except `/healthz`; sessions expire after an hour idle and are capped at 1000 (least recently used evicted).

## Setup

```bash
uv venv --python 3.12 .venv && source .venv/bin/activate
uv pip install -e ".[dev,api]"

# 1. Provision the restricted role on the Atlas database (as the Atlas owner)
python -m promptquery.atlas.security postgresql://OWNER@HOST:5432/atlas > sql/atlas_bot_role.sql
psql postgresql://OWNER@HOST:5432/atlas -v bot_password='...' -f sql/atlas_bot_role.sql

# 2. Configure (see .env.example) and run
export ANTHROPIC_API_KEY=...
export PQ_DSN=postgresql://atlas_bot:...@HOST:5432/atlas
export PQ_ADMIN_DSN=postgresql://OWNER@HOST:5432/atlas   # only to resolve a tenant slug
export PQ_TENANT=acme                                    # slug or UUID
prq-atlas ask "What is our total open receivable?"
prq-atlas chat                                           # up to 6 turns
uvicorn promptquery.api.app:app_factory --factory        # POST /chat {message, session_id}
```

HTTP: `POST /sessions`, `POST /chat`, `GET /sessions/{id}`, `DELETE /sessions/{id}`, `GET /healthz`.
Each `/chat` response carries `sql`, `columns`, `rows`, `row_count`, `truncated`, `answer_text`,
`standalone_question`, `intent`, `status` (`ok|refused|clarify|error|turn_limit`), `notes`, `error`.

## Evaluation

`eval/atlas/` holds 92 scenarios / 197 turns (16 six-turn, 10 of 3-4 turns, 66 single-turn; 52 dev, 40 held-out; 7 refusal turns) across
finance, sales, procurement, inventory, manufacturing, HR, CRM, projects, quality, maintenance and
hospitality, run against the demo tenants and the 100k-line `volume` tenant. Each turn has a gold
SQL executed through the same scoped path; the comparator checks execution accuracy (column
order/names ignored, numeric tolerance, row multiset or ordered for top-N, extra identifying
columns tolerated).

```bash
python -m eval.atlas.run --split dev --mode both --cache .cache/llm --out report.json
python -m eval.atlas.run --split all --oracle        # harness self-check (gold SQL as the model)
python -m eval.atlas.run --split dev --fail-under 0.95
```

Reported: end-to-end per-turn accuracy, teacher-forced per-turn accuracy (isolates follow-up
understanding from error propagation), per-scenario accuracy, by tag / turn index, refusal
accuracy, SQL-executed and repair rates, latency. Tune on `dev`; run `heldout` only at milestones.

Scenario hygiene is enforced by `tests/test_eval_scenarios_live.py`: every gold must validate, run
and return rows (an empty gold would accept any empty answer), and every question text must map
to one gold.

## Tests

`pytest` runs 246 offline tests. Setting `PQ_TEST_OWNER_DSN` and `PQ_TEST_BOT_DSN` (a seeded Atlas
database with the bot role applied) enables 84 more live tests (330 in total): role/RLS/denied-column
checks, tenant isolation, pack-vs-database drift (no orphan joins, every real enum value declared),
every metric, example and scenario query, full-stack conversations with a scripted model, and a
57-query battery of realistic PostgreSQL (window functions, `FILTER`, `DISTINCT ON`, `FETCH FIRST`,
`generate_series`, CTEs, set operations) proving the validator's rewrite returns exactly the same
rows and column names as the original SQL. That battery found a real bug (`FETCH FIRST n` was
silently replaced by the row cap), so extend it whenever a new construct shows up in model output.

CI (`.github/workflows/ci.yml`) runs lint, the offline suite on Python 3.10-3.12 and a build. The
`atlas-live` job clones Atlas, migrates and seeds it, provisions the role and runs the live tests
plus the oracle self-check; it is non-blocking because Atlas changes independently, and has not been
run on GitHub yet.

## Known limits

* Model accuracy is measured with `eval.atlas.run` and a live key. The offline suite proves the
  pipeline, safety and plumbing but cannot prove model quality. No accuracy figure has been
  measured yet; the 95% target is a design goal until that run is done.
* Sessions are in-memory (single process, bounded). Use a shared store before running several workers.
* Requests are serialised behind one lock and one database connection.
* The pack describes Atlas migration 0053; run the live pack tests after upgrading Atlas.
* Self-consistency voting was deliberately not built: at temperature 0 the candidates are identical,
  so it would need sampling support and a measured gain first.
* The original `promptquery` CLI is kept as upstream built it (plus the stricter base validator);
  the hardened, multi-turn path is `prq-atlas` / the HTTP API.
